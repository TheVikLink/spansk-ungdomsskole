# Isolert retensjonsjobb – klargjøring for syntetisk staging

Beads: spansk-ungdomsskole-twkq. Eier ber om trygg løsning og ferdig testunderlag. Ingen gjenbruk av utløpte operatorer eller avviklet fixture; ingen endring av appens alias, Feide eller produksjonsdata. Eksisterende isolert codex/pilot-auth-school-lifecycle videreføres, uten å røre skitten hovedarbeidskopi.

## Beslutning og leveringsgrense

Eget Vercel-prosjekt, foreslått navn spansk123-retention-staging, i eksisterende team theviklinks-projects. Kun en liten Node22-worker og eksisterende pg/zod-avhengigheter. Ingen Express-app, Feide, webdatabasekonto, Supabase SDK/service_role, adminnøkler, Vault eller pg_net. To nye tidsavgrensede NOINHERIT-loginroller uten gruppemedlemskap, ADMIN/SET/migrator, får kun USAGE/EXECUTE på nye funksjoner i privat retention_stage-skjema. De eksisterende brede retensjonsgruppene skal ikke arves. TLS validerer CA og vert. Prosjektet må ikke kobles til Git-autodeploy eller teamdelte sensitive miljøvariabler/integrasjoner; ingen nye leverandører.

Klargjør lokal worker, låst pakkemanifest, rollemaler, syntetisk testprotokoll og bevis før ekstern godkjenning. Denne bestillingen om klargjøring gir ikke produksjonsdeploy på dagens app. Vercel-native cron bruker GET mot Production-target, dokumentert https://vercel.com/docs/cron-jobs og /manage-cron-jobs (14.10). Derfor: default pakke har ingen crons og kun manuelt autentisert POST i Preview. Etter egen konkret godkjenning kan samme separate stagingprosjekt få Production-target for tidsstyring; det navnet er plattformens deploymål, ikke tilgang til produksjonsdatabaser. Ingen alias til app.spansk123.no.

## Data- og trusselmodell

Worker får bare dedikerte stagingretensjons-passord og tilfeldig CRON_SECRET(min32tegn), offentlig CA, en eksplisitt fixture-/policyversjon og absolutt slutttid. Ingen frie databaseURL-er, HTTPmål, bruker-/skoleparametre eller frister i request. Databasevert er aws-0-eu-north-1.pooler.supabase.com:5432, prosjekter peglwndjqnrstwnlrdsa/quznpkwsapehdcmicgsq og dedikerte brukernavn er kodekonstanter. Operasjoner bruker eksisterende SQL-policy, med maks20oppgaver og100tekniske rader per kategori. Ingen global teknisk opprydding i første test: den kan berøre andre fixtures. Konto-/skoleavvikling, eksport, journalopprydding og backup slettes ikke av jobben.

Konfigurasjonen inneholder én ny syntetisk skole-ID og policyversjon, aldri avviklet b76aeea7 eller gammel d7d3415b. Ny fixture/policy må godkjennes konkret før opprettelse. Worker kaller cleanupSchool bare med denne faste scopeverdien, ikke retention_targets og ikke requestdata. Forespørselsrespons og logger viser bare ok/failed og antall, ingen skole-ID-er, rårader, SQLfeil, passord eller tokens. Eksisterende prepare/apply sikrer journal før læringssletting og DB-låser før journal; journalfeil ruller apptransaksjonen tilbake. Retry er idempotent. Ingen feil fanges og omgjøres til ok.

Avvis oppstart før DB ved manglende/utløpt testvindu, feilVercelprosjekt/team, admin-/web-/Feide-miljøvariabler, feil rollenavn, ugyldig skole-ID, ugyldig CA eller cronhemmelighet. Ikke prøv å slette miljøvariabler. Faktisk ekstern miljøinspeksjon skal vise bare variabelnavn og pass/fail, aldri verdier. Vercels plattformmetadata/OIDC kan finnes; ingen kode bruker dette til andre tjenester. Prosjektisolasjon og avgrensede DBgrants, ikke env-skrubbing, er hovedbarrieren.

Manuell POST tillates bare eksakt /api/retention uten query/body. Cron-GET default av; aktivering krever separat konfigurert flagg samt samme hemmelige Authorization Bearer. User-Agent er aldri autentisering. Bruk hash/timingSafeEqual, no-store/private, ingen CORS, ingen redirects, cookie-/browserlogin eller user input som styrer apply. Det er en bevisst avgrenset unntaksdesign fra tidligere forbud mot offentlig muterende GET: bare autentisert maskinendepunkt i separat prosjekt, ingen tilgang med anonym/Feideøkt. Første Preview beholder plattformbeskyttelse og bruker godkjent maskintilgang; ikke slå den av.

## Samtidighet, tidsbruk og status

Gjenbruk cleanupSchool og SQL-barrierer fra verifisert kode; DB lock55P03 er en ikke-vellykket kjøring, ingen skjult retry. Kun én skole per invocation og én poolklient per DB, statement_timeout5s/journal5s og connection_timeout5s, idletransaction10s. maxDuration60s. Parallelle kall kan ikke slette samme låste batch; journalen er idempotent. Operatør må teste to samtidige kall og mistet journal etter prepare. Serverless prosessavbrudd kan etterlate committed journal; dette skal nekte appvisning frem til neste vellykkede apply/replay. Ingen automatisk gjenåpning bak journalen.

Jobbrun skal lagres med eksisterende begin_job/finish_job og generisk feil, bare tellere. Helse/status kan leses med autentisering og viser sist fullført/feilet og alder, aldri rårader. Manglende/ufullført kjøring over forventet intervall må vises som stale/failed, ikke healthy. En uavhengig observatør er nødvendig for å oppdage at cron aldri nådde workeren; ikke påstå bemannet varsling uten kanal og end-to-end alarmtest. I første pakke klargjøres observatør som lokal read-only kontrollkommando med pass/fail og injisert stale-test. Ingen e-post sendes automatisk i denne leveransen. Faktisk tidsstyring+alarm/varsling er fortsatt egne acceptanceporter.

Helseporten må skille manuell Preview og cron: hver pakke er bundet til ett forventet Vercel-prosjekt og testvindu, og hver DB-run får lane manual eller scheduled. Scoped health for scheduled ser bare faktisk cron-lane; manuell test og gamle job_run-rader kan ikke gjøre den frisk. Preview kan bare opprette manual-rader; cron-lane krever den separat aktiverte cronkonfigurasjonen og samme autentisering. Plattform-UA/header gir ikke selvstendig autentisering. Lokal observatør kontrollerer scheduled-lane; ingenkjøring, failed, running og stale gir ikke-ok. Bare faktiske scheduled-runs gir ekstern bevisstatus, ikke en test som sender samme headere lokalt.

## Test og gjennomføring

Test-first: autentisering/metode/body/query, miljøavvisning, fastscope, timeout/TLS, utløp, journalfeil/rollback, to invocations, sanitizer, jobrunfeil og staleness. Bruk ekte lokale PostgreSQL for journalføringsrekkefølge/samtidighet og minsteprivilegium; unit-fakes beviser bare HTTP-/konfigurasjonsadferd. Bygg selvstendig workerpakke fra allowlist og låst dependencylock, kontrollér ingen app-/envfiler eller symlinks tas med. Full test:all før levering, men ikke endre selve appens gatekilder/installerte migreringer.

Ekstern godkjenningspakke skal oppgi prosjektnavn, eksakte to nye DBroller, nyfixtureUUID, testvindu, preview-only manuell test og egen eventuell Production-target-cronbeslutning. Ikke bruk gamle operatorfiler eller legg inn secrets før godkjenning. Ekstern prøving: utenauth401, feilmetode405, tomrapport førgrense, kunutløptinnhold slettet, bevaraktivtinnhold/andretenant, journalfeil girfailed ogingenlæringssletting, repeat/samtidigkall, toekte scheduledruns+staleobserverførcronlukkes. Steng cron/login/policy og slett nye secretfiler ved testslutt. Ingen pilotklarpåstand før alle nødvendige eksterne porter er dokumentert.

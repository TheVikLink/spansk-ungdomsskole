## Neste handlinger som lukker de nåværende blokkeringene

1. **Oversikt AS kan vedta internt:** fyll beslutningsarket nedenfor (leverandørvalg for syntetisk staging, navngitte drifts-/personvernroller, administratorer/MFA, foreslåtte interne frister og retensjon, pilotlås). Disse punktene krever produkteeiers svar; de er ikke vedtatt bare fordi de står som anbefaling.
2. **Feide callback og klient:** Lokal server-side `form_post` med syntetisk OIDC-provider er implementert og servertestet med Node 22.23.3. Før callback sendes gjennom Vercel, undersøk Preview-loggfeltene med syntetisk POST. Opprett deretter en separat Sikt-testkonfigurasjon med bare `openid` + `userinfo-name`, eksakte routede URI-er og testbrukere aktivert. Ikke opprett produksjonskonfigurasjon eller publiser tjenesten ennå.
3. **Supabase staging:** skjermbilder 3.10 viser registry-raden for migrering 008, Advisor 0/0/3, korrekt `proconfig={search_path=pg_catalog}`, `postgres` uten SET-tilgang til `app_migrator` og migratoren NOLOGIN. `app_runtime` er LOGIN, ikke SUPERUSER/BYPASSRLS og ikke eier; de tre interne tabellene eies av migratoren, RLS er aktivt uten policies, og runtime har SELECT-grant. Produkteieren utførte direkte read-only runtime-test: `current_user=app_runtime`, RLS aktivt og 0 synlige rader i alle tre tabellene; transaksjonen ble rullet tilbake. A28 er lukket for denne avgrensede kontrollen. Ikke kjør migreringen igjen, gi SQL Editor-rollen SET-medlemskap eller opprett policies. Data API er fortsatt av. Gå videre med øvrige stagingporter og syntetisk Preview-verifikasjon; den historiske readiness-503-en er sendt til teknisk support. Knytt gjentatte 503/5xx til supportsaken. Admin-SELECT alene er ikke appbevis.
4. **Vercel og Supabase leverandørbevis:** Supabase har bekreftet standard-DPA via ToS, mottatt detaljert personvernoppfølging og en Dashboard-supportsak om readiness-503. Vercel har ikke svart per siste kontroll. Følg opp via planens supportkanal hvis svar uteblir. Når svarene kommer, før konto-/plan-/prosjektspesifikke opplysninger om logger, datafelt, lokasjoner, support, sekundærbruk/AI, backup/retensjon og revisjon mot hvert A-punkt, DPA og portalens svar. Ingen ekte elevdata eller Feide-callback før callbackparametere og logging er testet.
5. **Skoleeier før pilot:** når leverandør- og teknisk vedlegg er komplett, må den enkelte skoleeier beslutte roller, formål/grunnlag, DPIA-behov, retensjon, informasjon, avtale og pilotgodkjenning. Oversikt kan levere underlaget, men kan ikke skrive dette vedtaket på skolens vegne.

Dette er en sekvens med eksplisitte stoppunkter. Det finnes ingen saklig måte å «svare ferdig» på spørsmålene som tilhører Sikt, leverandørene eller skoleeier før de gir sine svar; uavklart status skal beholdes framfor å registrere antakelser som fakta.

## Hvilke svar kan ikke Oversikt fylle ut alene

Sikt må bekrefte konto-/tjenestespesifikk OIDC-konfigurasjon og testtilgang. Vercel og Supabase må svare om egne logger, støtte, behandling, underdatabehandlere og plattformkontroller. Skoleeier må avgjøre behandlingsgrunnlag, DPIA, informasjon og aksept av leverandør-/overføringsrisiko.
